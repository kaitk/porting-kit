# Internationalization in a port

The API answers the same bytes in every locale; text in the user's language comes from the
client and from the page renderer, which carry the app's translations. Then the Rust server
holds no translations, and the byte comparison checks every locale at once.

## The API answers keys, not text

A refusal carries a stable key and its parameters, which the client translates, and at
most an English message for people reading the API. A survey looks for the server
translating text itself: i18n calls in server modules, and schema messages that call the
i18n library, since those run on the server in the request's locale. Each one is a change
to the app before the port (2026-10-22):

- Snowtime's valibot messages called Paraglide, so a session in Estonian got Estonian text
  in a 400, against the API's own documentation, and the client showed a generic error
  anyway. Snowtime task 094 records each message's key and parameters for its issue,
  answers `{ key, params, message }` with the message in English, and lets the client
  translate the key; the browser's forms still show the schemas' translated text.
- Better Auth's routes already answered a stable code with an English message, which the
  client maps to translated text: the pattern the API follows.

## Pages render in the user's language

The render bundle carries the app's translations and picks the locale as the app's i18n
middleware does, from the locale cookie and `Accept-Language`; the host passes both with
each page request. The engine needs `Intl` for the app's locales: V8 has it, while
QuickJS needed polyfills and was rejected for that and its speed
([the frontend recipe](../recipes/frontend/solid-start.md)).

## Locale-dependent server logic

- **Sorting.** JavaScript's `localeCompare` uses Unicode collation; the port matches it
  with ICU4X (`icu_collator`, pure Rust) in the locale the TypeScript server runs in.
  Snowtime's runs `en-US` (snowtime-native `crates/server/src/reports/aggregation.rs`).
- **The locale cookie.** Saving a user's language and signing in set it; the port sets
  the same cookie with the same attributes, which the session conformance test checks.
- **Dates and days** follow the user's time zone setting, not the locale.

## Verify

Run the conformance suite and the byte comparison with at least one session in a locale
other than the default, and compare pages rendered in each locale.
